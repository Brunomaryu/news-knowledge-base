## 目的

業界ニュースを**ファクト・背景・示唆**の3層で構造化してNotionに蓄積し、コンサルティング業務での知識活用・提案品質向上を実現する。

---

## アーキテクチャ

```
[入力]                    [処理]               [格納・活用]
手書きノート  ──┐
Web記事      ──┼──▶ Cowork AI ──▶ Notion DB（3DB）──▶ 検索・分析
会議・対話   ──┘    (Notion MCP)   ニュースDB           週次サマリ
                                   企業DB               業界レポート
                                   業界DB               コンサル活用
                                       ↓
                                   定期バックアップ
                                   (scripts/export_notion.py)
```

### 設計原則（v1.2.0）

| # | 原則 | 内容 |
|---|---|---|
| 1 | **Notionがマスターデータ** | 本リポジトリはルール・設計定義のみ管理。データの正本はNotion |
| 2 | **3層構造** | Fact（核心）/ 背景（文脈）/ 示唆（コンサル視点） |
| 3 | **検索可能性優先** | 業界・タグによる多軸検索を保証 |
| 4 | **削除しない** | 一度登録した記事は原則保持（知識資産）。変更は追記・差分で管理 |
| 5 | **個人利用前提・過剰設計禁止** | 保守コスト < 得られる価値、を常に判断基準とする |
| 6 | **後方互換性維持** | 既存フィールド・フローを壊す変更は段階移行を経る |
| 7 | **将来Agent化に備えた設計** | 各フローを「Input→Judge→Output」で記述し、マルチエージェント化に備える |

**フィールド設計（v1.2.0）**

| フィールド | 型 | 必須 | 役割 | v1.2変更 |
|---|---|---|---|---|
| Fact | title | ✅ | 記事の核心ファクト（1行・検索のメインキー）。事実のみ記載 | - |
| 背景 | text | 推奨 | ニュースの背景・前提・文脈 | - |
| 示唆 | text | 推奨 | コンサル視点での示唆（推奨フォーマットあり） | フォーマット追加 |
| 業界 | multi-select | 推奨 | 業界カテゴリ（10分類、最大3個推奨） | - |
| タグ | multi-select | 推奨 | テーマタグ（40種、**最大5個**） | 上限ルール明示 |
| 日付 | date | 推奨 | 記事日付（YYYY-MM-DD） | - |
| 出典URL | url | 推奨 | 記事の元URL（重複チェック・引用に使用） | **新規追加** |
| 媒体名 | text | 推奨 | 出典メディア名（例: 日経・Bloomberg等） | **新規追加** |
| 関連記事 | relation | 任意 | 同テーマの関連記事へのリレーション | **新規追加** |
| Summary | text | 任意 | 要約（旧フィールド、互換性のため保持） | - |
| 業界／国 | text | 任意 | 旧業界フィールド（参照用、廃止予定） | - |

**示唆フィールドの推奨フォーマット（v1.2.0追加）**

```
【何が変化したか】
（市場・技術・規制・企業行動の具体的変化を1〜2行で）

【なぜ重要か】
（業界・顧客・競合への影響理由）

【誰へ影響するか】
（プレイヤー名を具体的に）

【波及先・連鎖効果】
（サプライチェーン・隣接業界への影響）

【コンサル活用】
（提案・分析・仮説設定での活用イメージ）

【Action】（任意）
（次に調べるべきこと・確認すべきことがあれば）

確度: ✅確実 / 🔶推測 / 💡仮説
```

> 推奨フォーマット。短い記事・速報は自由記述も可。質より量を優先する期間は簡易記述で登録してよい。

- `obsolete`：大幅な組織変更・M&A等で既存情報が無効になった場合

## AI役割定義（v1.2.0追加）

現在は単一AIが全役割を担うが、以下の論理的役割分離を設計上定義する。将来のマルチエージェント化に向けた設計ドキュメントとして活用。

| 役割 | 担当フロー | Input | Judge | Output |
|---|---|---|---|---|
| **Ingest Agent** | 記事追加・一括登録 | 生のニュース情報 | 構造化・分類・重複チェック | Notion登録 |
| **Analyst Agent** | 週次サマリ・分析 | Notion記事群 | テーマ抽出・横断分析 | サマリ・レポート |
| **Curator Agent** | 企業DB・業界DB更新 | Notion記事 + WebSearch | 情報統合・差分判断 | DB更新 |
| **QA Agent** | タグ整合性・バリデーション | 全Notion記事 | ルール照合 | エラーレポート |

## バリデーションルール（v1.2.0拡張）

詳細は `tests/validation_rules.md` を参照。

| # | チェック項目 | 優先度 | 自動化 |
|---|---|---|---|
| V-1 | タグが taxonomy.md の許容値内か | 高 | 手動（将来スクリプト化） |
| V-2 | 業界が taxonomy.md の許容値内か | 高 | 手動 |
| V-3 | タグ数が5件以内か | 中 | 手動 |
| V-4 | 業界が未分類（空欄）の記事がないか | 中 | 手動 |
| V-5 | Factに推測表現（〜と思われる・〜だろう等）が混入していないか | 高 | 手動 |
| V-6 | 出典URLの重複がないか（同一記事の二重登録） | 中 | 手動 |
| V-7 | 必須項目（Fact・業界・タグ）が空の記事がないか | 高 | 手動 |
| V-8 | 企業DBの「情報ステータス」が要確認・obsoleteでないか | 中 | 手動 |
| V-9 | 業界DBの「最終更新日」が3ヶ月以上古くないか | 低 | 手動 |

## 更新フロー（企業DB・業界DB）v1.2.0

企業DB・業界DBの全面更新時は、以下の擬似Draftフローを必ず踏む：

```
① AIが更新対象ページの現在の内容をチャットに表示
        ↓
② AIが変更予定内容を「変更前 → 変更後」の差分形式で提示
        ↓
③ ユーザーが承認（Yes / 修正指示）
        ↓
④ notion-update-page を実行
```

> Notion APIにDraft機能はないため、チャット上での確認フローで代替する。
